# rswirelesscrafting 全量审计报告（第二轮）

- 日期：2026-10-28
- 基线：`main` @ `3486e97` 及当前工作区未提交改动
- 范围：common / NeoForge / Fabric 的全部功能模块、菜单、权限、能量、存储、区块生命周期、资源、文档
- 方法：源码审查 + RS2 2.0.7 参考实现对照 + 玩家操作链路推演 + 构建与单元测试
- 验证：`./gradlew -I init-mirror.gradle build` 通过；7 个 JUnit 测试通过；未做 Minecraft 实机、专用服务器和旧存档迁移验证

> 本报告是对当前实现的第二轮独立审计，不沿用上一轮“已完成”的判断。重点放在“功能是否真的成立”，而不是只看类是否存在、界面是否能打开。

---

## 1. 总体结论

**当前仍不适合发布。**

本轮新确认的最高优先级问题是：**网络桥接器的存储视图没有接入 RS 的复合存储缓存通知机制**。这会导致桥接器看起来已经绑定，实际却让本地网络看到空库存或过期库存。它不是 UI 小问题，而是网络桥的核心功能不成立。

另外还有几组会改变玩法结果的问题：

- 无线桥在红石挂起、配置关闭或欠费时仍然扣电。
- 增幅塔在网络没电后仍保持激活，折扣继续生效。
- 多个自动合成/补货路径没有完整的权限或扣费前置检查。
- 虚拟样板终端的终端物品可以在界面打开后被移动，而虚拟网格没有对应的有效性校验。
- 监控终端、充电站、无线桥和批量配置粘贴存在多人权限边界问题。
- 静态登记表没有区分客户端/服务端或世界生命周期，集成端切换世界/卸载区块时可能互相删除状态。

建议先发修复版开发构建，完成 P0/P1 修复后再做实机测试。不要只凭当前构建成功就发正式版。

## 2. 按严重程度排列的问题

### P0-1：网络桥接存储缓存失效，桥接后可能一直显示空库存

**位置**

- `common/networkbridge/BridgedStorage.java:46-89`
- `common/networkbridge/NetworkBridgeNetworkNode.java:40-49`
- RS 参考实现：`CompositeStorageImpl.addSource` / `getAll`

**触发条件**

1. 放置网络桥接器。
2. 节点自动加入本地网络时，桥尚未绑定远端，`BridgedStorage.getAll()` 返回空。
3. RS 的 `StorageNetworkComponent` 把这个空存储源加入 RootStorage。
4. 之后玩家再绑定远端网络。

或者：桥已绑定，但远端网络中的物品发生插入、提取或掉线/重连变化。

**实际影响**

RS 的 `CompositeStorageImpl` 在 `addSource()` 时把 `source.getAll()` 复制进缓存列表，之后 `getAll()` 返回的是缓存，不是每次重新遍历源。当前 `BridgedStorage` 没有实现 `CompositeAwareChild`，也没有在远端变化时通知父级缓存：

- 绑定前为空时，RootStorage 缓存可能一直为空；
- 已绑定时，远端库存变化不会反映到本地列表；
- `getStored()` 可能显示远端总量，而网格列表/自动补货仍看不到对应物品；
- 玩家会遇到“桥接显示已连接，但终端没有物品、监控存量为 0、自动合成判断缺料”的状态。

**修改建议**

- 让桥接存储实现 `CompositeAwareChild`，维护父级 `ParentComposite` 集合。
- 在远端网络从 null 变为可用、解除绑定、重新绑定时，做完整的旧缓存移除/新缓存加入。
- 对远端库存变化建立通知或受控的刷新机制，至少保证本地插入/提取、远端网络重连、定时同步时刷新缓存。
- 不要简单在每次 `getAll()` 中无界遍历所有远端物品，需限制刷新频率和大型网络的成本。
- 加集成测试：先放置后绑定、绑定后远端插取、解绑重绑、重进世界、远端网络断开再恢复。

这是发版前必须修复的问题。

### P1-1：无线桥在红石挂起、配置关闭、欠费时仍然扣电

**位置**：`common/bridge/WirelessBridgeBlockEntity.java:124-147, 262-270`

**触发条件**

- 无线桥已配对。
- 打开红石信号、关闭 `bridge.enabled`，或远端网络欠费/消失。

`sync()` 会设置 `linked=false`，但 `tick()` 随后仍无条件调用 `consume(config)`。`consume()` 只检查 `mainNetworkNode.getNetwork()`，不检查 `linked`、`suspended`、`unpaid` 或 `config.isEnabled()`。

**实际影响**

- 红石“挂起省电”的文案不成立。
- 配置关闭后仍然产生桥本身和保活区块的费用。
- 欠费时继续抽本地网络能量，可能让玩家以为链路已经停了但电量仍在下降。
- 保活区块和链路费用的状态无法通过右键反馈准确判断。

**修改建议**

在 `consume()` 入口统一判断当前是否允许运行：配置开启、未挂起、未欠费且 `linked == true`。如果产品决定“保活也要单独收费”，应拆成两项独立费用，并明确显示，不能隐式扣费。

### P1-2：增幅塔没电后仍然提供折扣

**位置**：`common/amplifier/AmplifierBlockEntity.java:65-90`

**触发条件**

塔接入网络后，`network != null`，但网络电量为 0 或不足以支付本 tick 消耗。

**实际影响**

`active` 只看配置、网络对象和红石，不看能量余额。`ACTIVE` 仍为 true，`AmplifierRegistry` 继续给终端打折，同时 `extract()` 只返回部分电量或 0。玩家获得免费增幅效果。

**修改建议**

- 激活前检查本 tick 的费用是否可支付。
- 实际扣费不足时立即停用，而不是保持 ACTIVE。
- 将“无网络”“欠费”“红石挂起”“配置关闭”分别反馈给玩家。

### P1-3：无线桥同时留在本地网络和远端网络，节点归属与能量统计错误

**位置**

- `common/link/NetworkAttachment.java:81-99, 116-121`
- `common/bridge/WirelessBridgeBlockEntity.java:73-79, 177-179`

**触发条件**

无线桥据点贴着本地 RS 线缆放置。基类先自动加入本地网络，之后 `ensureAttached()` 又把它加入远端网络，没有先从本地网络 `removeContainer`。

**实际影响**

同一个容器同时存在于两张网络：

- 节点 `getNetwork()` 被改写成远端网络；
- 本地网络仍保留容器引用；
- 桥自身的能量/节点统计可能被两张网络重复计算；
- RS 图重建后可能出现本地/远端归属反复变化。

**修改建议**

明确每个桥接节点的唯一归属。进入远端网络前先从原网络摘除；如果产品需要同时保留两种身份，应拆成两个独立容器/节点，不能让同一个节点对象同时挂两边。

### P1-4：虚拟终端先按未乘倍率的价格检查，导致动作发生但费用不足

**位置**：`common/virtual/VirtualTerminalSession.java:45-65`

**触发条件**

玩家在有距离倍率或跨维度倍率时使用样板终端、自动合成仓管理器、监控终端。

**实际影响**

`tryCharge()` 先调用 `canAfford(baseCost)`，再调用 `context.drainEnergy(baseCost)`。后者会乘距离倍率，但 `canAfford()` 只比较未乘倍率的 `baseCost`：

- 例如基础打开费用 5 FE，跨维度实际 80 FE；
- 网络或电池只有 5 FE 时检查通过；
- 动作随后发生，网络可能只被抽走部分费用，终端仍然打开。

**修改建议**

- 在 session 中保存玩家上下文，先计算与 `ExtendedWirelessNetworkItemContext` 相同的实际费用，再检查余额。
- 最好统一使用 `AbstractWirelessTerminalItem.actionCost` / `tryConsumeEnergy`，不要维护第二套费用计算。
- 测试同维度远距离、跨维度、远程输电插件不足额和电池不足额。

### P1-5：合成网格的自动合成等操作先执行后扣费，可能欠费完成

**位置**：`common/wirelesscraftinggrid/WirelessCraftingGrid.java:165-170, 183-190, 215-220, 308-320`

**触发条件**

终端或网络剩余能量不足以支付实际动作费用。

**实际影响**

- `startTask()` 先创建任务，再调用 `drainEnergy()`，任务可能已经成功创建但没有付够钱。
- `addWatcher()`、清空矩阵、配方转移也没有先做足额检查。
- `drainEnergy()` 是静默按可扣数量扣，不足额不会让调用方知道。
- 玩家可以用剩余少量电量完成本应付不起的操作。

**修改建议**

- 为每类操作在动作前做足额预检，失败则不创建任务、不清空、不转移、不添加 watcher。
- 成功后再通过统一的 `tryConsumeEnergy` 扣费。
- 对不可回滚的操作尤其要先预检，不能依赖事后发现欠费。

### P1-6：监控终端没有 OPEN 权限检查，后台补货还绕过 AUTOCRAFTING 权限

**位置**

- `common/monitor/WirelessMonitorItem.java:60-75`
- `common/monitor/MonitorEngine.java:63-90, 117-141`
- `common/monitor/WirelessMonitorContainerMenu.java:184-241`

**触发条件**

玩家把监控终端绑定到他人的或受保护的网络。

**实际影响**

- 打开监控界面时不像其他终端一样调用 `SecurityHelper.isAllowed(OPEN)`。
- 后台只凭绑定坐标就读取库存。
- 补货直接 `ensureTask`，没有 `AUTOCRAFTING` 权限检查。
- 菜单按钮也没有重新校验当前权限。

**修改建议**

- 打开界面、刷新数据、点击按钮时校验 OPEN。
- 后台补货校验 AUTOCRAFTING，必要时同时校验读取权限。
- 使用持久化的授权玩家 UUID，在 tick 中复核权限变化。

### P1-7：充电站没有网络安全边界，任何玩家都可能消耗网络能量

**位置**

- `common/chargingstation/ChargingStationBlock.java:91-106`
- `common/chargingstation/ChargingStationBlockEntity.java:119-146, 251-277, 313-337`

**触发条件**

- 未授权玩家右键充电站并放入自己的 FE 物品。
- 未授权玩家站在充电站无线范围内。
- 充电站连接到受保护网络。

**实际影响**

打开界面和无线充电都没有 `SecurityHelper` 检查。其他玩家可以使用网络能量给自己的设备充电，甚至只是站在附近就受益。

**修改建议**

- 打开界面前检查 OPEN。
- 充电动作按站主/绑定玩家权限检查，后台也定期复核。
- 明确无线充电是“公共区域服务”还是“仅授权玩家可用”，不要让默认行为绕过安全网络。

### P1-8：无线桥配对没有 RS 权限校验，可向受保护网络延伸节点

**位置**：`common/bridge/WirelessBridgeBlockEntity.java:101-110, 152-179`

**触发条件**

玩家在他人的网络方块旁放置无线桥，记录其为基点后完成配对。

**实际影响**

桥节点直接加入目标网络，没有检查玩家是否有权使用该网络。之后在据点旁接 RS 总线，就可能把受保护网络的物品/能量暴露出来。

**修改建议**

- 配对时检查目标网络的 BUILD/OPEN/EXTRACT 等适当权限。
- 保存授权玩家 UUID，tick 中复核，权限撤销后断链。
- 对“物理接触即授权”的规则要单独写清楚，不能默认绕过 RS 安全系统。

### P1-9：能量接收器/监控仪在目标未加载时跳过权限验证，之后可直接工作

**位置**

- `common/energyreceiver/WirelessEnergyReceiverBlock.java:134-139`
- `common/energymonitor/EnergyMonitorBlock.java:148-153`

**触发条件**

绑定时目标区块未加载，随后目标区块恢复加载。

**实际影响**

`canBind()` 对 `BoundTargetResolver.resolveNetwork(...)` 为空时 `orElse(true)`，因此绑定阶段不检查权限。后续 tick 也没有对应的授权玩家复核。

接收器可以向受保护网络注能并收链路费；监控仪可以读取其能量数据。

**修改建议**

- 绑定和激活分开处理：未加载时只能保存目标，不能视为已授权。
- 保存授权 UUID，目标恢复后先验证再允许工作。
- 权限校验失败时显示“无权限”，不要显示成普通的“未连接”。

### P1-10：虚拟样板终端没有终端物品有效性校验，移动物品后仍可编辑旧对象

**位置**

- `common/patterngrid/VirtualPatternGrid.java:63-78, 98-116`
- `common/patterngrid/WirelessPatternGridMenuProvider.java:37-56`

**触发条件**

打开无线样板终端后，把终端从手上、背包或饰品槽移走，继续编辑样板。

**实际影响**

`VirtualPatternGrid` 持有打开时的 `ItemStack`，但菜单没有锁定终端槽，也没有 `stillValid` 身份校验。后续 `setChanged()` 仍向旧物品对象写状态：

- 新位置中的终端可能不是正在被编辑的物品；
- 玩家会看到“当前物品没有保存刚才的修改”或状态错位；
- 打开期间移动/丢弃/替换终端可能造成状态丢失或误写。

**修改建议**

- 菜单保存 `SlotReference`，每次校验仍解析到同一个物品对象。
- 像插件装配/监控界面一样锁住终端槽，或让虚拟菜单在物品移动时立即关闭。
- 为样板编辑状态增加“当前会话有效”的测试。

### P1-11：无线配置卡批量粘贴没有目标权限边界

**位置**：`common/configcard/WirelessConfigurationCardItem.java:113-149`

**触发条件**

玩家在包含其他玩家机器的区域潜行右键批量粘贴。

**实际影响**

每个同类型方块都会直接执行 `readConfiguration`，没有检查其所属网络或权限。相比原版单点配置卡，本模组把影响范围扩大到整个区域，可能误改或恶意改动别人的机器。

**修改建议**

- 批量前过滤无权限的网络/机器，至少检查 BUILD 或设备所有者。
- 只给明确可管理的目标粘贴，并报告“跳过 N 个无权限目标”。
- 默认缩小批量范围或要求二次确认。

### P1-12：网络桥接器的桥费可能只按余额判断，实际却没有足额扣除

**位置**：`common/networkbridge/NetworkBridgeBlockEntity.java:228-243`

**触发条件**

桥费大于桥接器的 `energyTransferRate`，或本地网络主要由远端桥接能量提供。

**实际影响**

代码先判断 `energy.getStored() >= fee`，再忽略 `energy.extract(fee)` 的返回值。余额包含远端能量时，实际抽取会受到桥接限速，可能只扣到一部分，但桥仍继续工作。

**修改建议**

- 要求实际 `extract(fee) == fee`，否则本次扣费失败并停止转发。
- 如果要让桥接能量参与自身费用，需明确限速和自付规则，避免“余额显示够、实际扣不够”。

### P1-13：分拣站没有走 `WorldlyContainer` 的侧面规则，目标容器兼容性不完整

**位置**：`common/smartsorter/SmartSorterBlockEntity.java:267-275`

**触发条件**

- 输出到熔炉、漏斗或其他实现 `WorldlyContainer` 的容器。
- 目标是一个需要区分输入面的机器。
- 输出到大箱子的某一侧。

**实际影响**

`outputTarget()` 直接把目标方块实体当 `Container`，没有按分拣站朝向使用对应输入面：

- 可能向熔炉输出槽或错误面写物品；
- 部分机器会拒绝或表现与 RS 输出总线不同；
- 大箱子可能只访问到一半容量。

**修改建议**

- 通过平台物品容器适配层访问目标，而不是直接操作 BE。
- 输入面使用 `getOutputSide().getOpposite()`。
- 用箱子组合容器或正确的 Capability/Storage 视图处理大箱子。
- 增加熔炉、漏斗、双箱和模组机器的测试。

### P1-14：增幅塔登记表在集成端客户端/服务端之间互相影响

**位置**：`common/amplifier/AmplifierRegistry.java:28-47`

**触发条件**

集成端中，服务端仍加载增幅塔，但客户端离开或卸载对应区块。

**实际影响**

`AMPLIFIERS` 是同一 JVM 的静态集合，只按维度区分。客户端 `setRemoved()` 会移除坐标，服务端的激活塔也因此从登记表消失，距离折扣失效。反过来，客户端重新登记后又可能与服务端状态混淆。

**修改建议**

- 按逻辑端或 `Level` 实例区分登记表，至少把 `level.isClientSide` 纳入 key。
- 不要让客户端卸载生命周期删除服务端状态。
- 增加集成端离开/返回区块的测试。

### P2-1：区块强加载引用计数没有跨重启恢复，配置关闭也有持久化边界

**位置**：`common/link/LinkRegistry.java:31-36`

`HELD` 只存在内存中，但 `ServerLevel#setChunkForced` 会留在存档里。重启后原强制加载记录仍在，引用计数却清零。之后其他方块释放时，可能错误释放仍被旧桥需要的区块；反过来，旧记录也可能永久残留。

`chunkLoadingEnabled=false` 目前按设计不主动释放已有区块，这可以避免死锁，但与“关闭即不加载”的直觉和配置注释不完全一致，需要明确说明，并处理重启后的清理/恢复。

---

### P2-2：配对剪贴板跨世界保留旧坐标

**位置**：`common/link/PairingClipboard.java:22-38`

`PENDING` 不按服务器/存档隔离，玩家退出一个世界再进另一个世界后，旧接入点仍在。若在新世界绑定，可能把设备指向新世界中相同坐标的另一个方块。

建议在服务器停止/世界卸载时清空，或记录服务器标识并设置过期时间。

### P2-3：监控仪换到另一个相邻网络后没有重置采样基线

**位置**：`common/energymonitor/EnergyMonitorBlockEntity.java:163-188, 220-235`

**触发条件**

未绑定的监控仪先贴在 A 网络旁，随后改放到 B 网络旁，中间没有断网。

**实际影响**

`lastSampleStored` 仍是 A 网络的存量，下一次采样会把 A→B 的存量差当作真实充放电速率，产生错误的大进/大出电量。

建议记录当前 `Network` 对象，网络身份变化时重置基线。

---

### P2-4：升级容器对异常的 5 个以上插件不会截断，隐藏插件仍然生效

**位置**：`common/upgrade/UpgradeContainer.java:27-49`、`common/upgrade/Upgrades.java:85-99`

**触发条件**

旧版本、其他模组或手工修改物品组件，使 `upgrades` 列表长度超过 4。

**实际影响**

界面只显示前 4 个，但 `hasUpgrade()` / `countUpgrades()` 遍历全部元素，后面的隐藏插件仍提供范围、维度、远程输电等能力。

建议读取时限制为前 4 个，或在迁移/写回时明确处理多余项，避免隐性功能。

---

### P2-5：配置热更新与显示值不一致

**位置**

- `common/energyreceiver/WirelessEnergyReceiverBlockEntity.java:59,75`
- `common/networkbridge/NetworkBridgeBlockEntity.java:53-67`

接收器容量和桥接器限速器在构造时读取配置，运行中修改配置不会同步到已有方块实体。tooltip/状态行可能显示新值，实际仍按旧值工作。

建议每次 tick 读取当前配置，或明确要求重载世界并提示。

---

### P2-6：多个能量/数量计算仍可能溢出

**位置**

- `common/util/RateMeter.java:18-22`
- `common/chargingstation/ChargingStationBlockEntity.java:251-257, 405-413`
- `common/hud/WirelessTerminalHud.java:90-94`

**触发条件**

管理员把速率/容量设为极大值，或插件/存档写入异常大数量。

**实际影响**

`carry + perSecond`、`wirelessChargeRate * intervalTicks`、`given * 100`、`stored * 4` 可能溢出，造成负速率、费用错误或 HUD 状态错误。

建议用饱和加法、先除后乘或 `Math.multiplyExact`，并限制配置上限。

### P2-7：超频 mixin 仍有 Shadow 映射警告，可能静默失效

**位置**：`neoforge/mixin/AbstractAutocrafterOverclockMixin.java:28-34` 及 Fabric 同名文件

构建日志有 `NO_OBFDATA_FOR_SHADOW`。`@Redirect` 使用 `remap=false`，但两个 `@Shadow` 字段没有同样明确处理。生产环境字段映射不匹配时，超频卡可能按设计安静失效。

建议实机验证 Fabric 和 NeoForge 生产环境，必要时给 Shadow 字段补充明确 remap 设置，并把失败情况写入兼容性说明。

---

### P2-8：分拣站虽然有方向，但模型没有正面差异

**位置**

- `common/smartsorter/SmartSorterBlock.java:55-77`
- `assets/rswirelesscrafting/models/block/smart_sorter.json`
- `assets/rswirelesscrafting/models/block/smart_sorter_active.json`

放置逻辑已经有朝向，但模型使用 `cube_all`，各面纹理相同，玩家无法从外观判断输出面，容易摆反。

建议使用定向模型和正面纹理，或在 GUI/右键状态中显示输出方向。

## 4. 与 RS2 的关系：合理沿用与需要区分的偏差

### 已核对，不应误报为本模组新 bug

- 无线网格的 `isGridActive()` 要求网络有能量，这与 RS2 `WirelessGrid` 的实现一致。它意味着“网络耗尽时终端即使自己有电池也可能无法继续操作”，不是本模组新增的逻辑；但文档应把远程输电插件的适用边界说清楚。
- 合成网格部分清空矩阵、快速合成后回写网络的路径与 RS2 `CraftingGridBlockEntity` 相近，不能仅凭“直接调用 RootStorage”就判定为本模组新引入的问题。新增设备的权限检查仍应单独审计。
- `BaseEntityBlock` 的 `RenderShape.MODEL` 已显式覆写，充电站不会走默认 `INVISIBLE`。
- `PatternGridBlockEntity` / `AutocrafterManagerBlockEntity` 的虚拟对象路线本身可行，但必须补会话有效性、权限和费用边界，不能只以“能打开菜单”作为完成标准。
- 分拣站按 `canPlaceItem` 做容量检查是正确方向，但它只覆盖普通 `Container` 路径，不能替代 `WorldlyContainer` 和平台 Capability 适配。

### 本模组新增、需要明确承担责任的偏差

- 网络桥让两张网络互相暴露库存/能量，比 RS 原生网络连接更复杂，必须处理缓存、环路、权限和限速。
- 无线桥自带区块保活，改变了 RS 对区块加载的成本结构，必须保证“断链路”和“扣费/保活”语义一致。
- 监控补货是后台自动发起合成，不再只是 RS 原生 GUI 操作，权限与费用必须独立于玩家是否正在看界面。
- 批量配置粘贴扩大了原版配置卡的作用范围，不能只按原版单点操作的安全假设处理。
- 分拣站是自定义输出设备，需要遵循 RS 输出总线的输入面和容器语义，而不只是实现“有箱子就能塞”。
