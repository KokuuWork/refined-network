## 0. 结论

**当前批次不能发布，也不具备“只差文档”的完成度。**

本批新增的 4 件内容（无线能量接收器、能量监控仪、智能分拣站、网络桥接器）方向正确，架构选择也基本合理，但目前处于“代码写完但未收口”的状态：

1. **原始项目无法编译**：`clean build` 失败，9 个编译错误；在隔离副本修掉后，checkstyle 又报 5 个违规。
2. **修掉这些机械问题后，两端可以构建成功**，说明没有更深层的 API 断链；这是好消息。
3. **仍存在会造成崩溃、物品丢失、权限绕过或功能不可用的 P0/P1 问题**，不能用“编译通过”代替验收。
4. **没有测试**；CI 使用 `-x test`，测试任务实际为 `NO-SOURCE`。
5. **新增内容的 83 个语言键没有生成**，中英文都缺；README、CHANGELOG、架构文档也没有收录这 4 件内容。
6. **CHANGELOG 声称“已全部实现、编译通过（两个加载器 + checkstyle）”，与当前事实不符**，会误导发布判断。

建议按本文第 7 节的顺序整改，先修 P0，再补 P1 和测试，最后更新文档与发版材料。

### N-1 网络桥自指/成环：栈溢出与存储错乱

相关代码：

- `networkbridge/NetworkBridgeNetworkNode.java:52-71`
  - `getStored()` 直接返回 `blockEntity.getRemoteEnergyStored()`
  - `getCapacity()` 直接返回远端容量
  - `extract()` 直接抽远端能量
- `networkbridge/NetworkBridgeBlockEntity.java:190-218`
  - `getRemoteEnergyStored()` 调用远端 `EnergyNetworkComponent.getStored()`
- `networkbridge/BridgedStorage.java:53-67`
  - 重入旗子只在**单个** `BridgedStorage` 实例内有效
- `NetworkBridgeBlockEntity.java:32`
  - 注释明确建议“想反向就再放一座指着回来的桥接器”

RS 的 `EnergyNetworkComponentImpl.getStored()` 是：

```java
for (EnergyProvider provider : providers) {
    stored += provider.getStored();
}
```

因此：

- 桥指向自己所在网络：本地网络总电量遍历到桥 → 桥再问本地网络总电量 → 无限递归，`StackOverflowError`。
- A 桥指 B，B 桥指 A：A 总电量 → B 总电量 → A 总电量 → …，同样栈溢出。
- 存储侧虽然 `BridgedStorage` 有 `forwarding` 旗子，但它只防止同一实例无限递归，**不能防止两个实例互相重复计入**；插入/提取可能重复经过同一条路径，导致缓存列表与实际源不一致。

这不是边界情况：玩家把桥贴在自家网络旁，直接绑定同一网络的线缆即可触发；而文档还主动建议双向桥。

**建议**：

1. 在解析远端网络后立即拒绝 `remote == mainNetworkNode.getNetwork()`，状态显示“不能桥接自身网络”。
2. 二选一：
   - **不支持双向**：移除“再放一座反向桥”的文案；绑定目标若已包含指向本网的桥，拒绝。
   - **支持双向**：建立全局桥接拓扑，检测环；或在能量/存储读取时使用共享的 `ThreadLocal<Set<Network>>` 递归守卫，并明确重复计入的处理策略。
3. 无论选哪种，都要给 `getStored`、`getCapacity`、`extract` 和 `BridgedStorage` 的插入/提取加环检测测试。
4. 在 `statusLine` 中区分“目标网络不可用”“不能桥接自身”“检测到环”。

**验收标准**：

- 自指绑定不崩溃、不改变库存/能量汇总；
- 双向绑定不崩溃，物品总量不因桥接而增加；
- 反复解绑/重绑后，两端库存与能量守恒。

### N-2 重新绑定/解绑泄漏旧网络容器

相关代码：

- `energyreceiver/WirelessEnergyReceiverBlockEntity.java:119-130`
- `bridge/WirelessBridgeBlockEntity.java:102-112`
- `link/NetworkAttachment.java:103-115`

三个方法都做了同一件事：

```java
this.target = ...;
this.attachment = null;  // 直接丢掉引用
```

但没有先调用 `attachment.detach()`。结果：

- 旧网络仍然持有这个节点容器；
- 接收器会继续被旧网络当成 `EnergyProvider`；
- 无线桥的据点会继续被旧网络当成节点；
- `setRemoved()` 只能 detach 当前引用，已经丢掉的旧 attachment 永远无法清理；
- 旧网络的存储/能量统计会被幽灵容器污染，且可能继续收/供电。

**建议**：

```java
public void bindTo(final GlobalPos anchor) {
    detachLink();          // 先清理旧网络
    this.target = anchor;
    this.syncCountdown = 0;
    setLinked(false);
    setChanged();
}

public void unbind() {
    detachLink();
    this.target = null;
    setLinked(false);
    setChanged();
}
```

同时检查无线桥的 `unbind` 与 `setRemoved` 路径；`NetworkAttachment` 可增加 `close()` 或 `isAttached()` 断言，方便测试。

**验收标准**：

- 绑定 A → 改绑 B：A 的 `getStored/getCapacity/getAll` 不再包含该节点；
- 解绑后：旧网络不再扣费/供电；
- 拆方块、重进世界、跨维度重绑均无幽灵节点。

```java
@Override
public boolean mouseClicked(final double mouseX, final double mouseY, final int button) {
    if (button == 0) {
        final int x = leftPos + SmartSorterContainerMenu.MODE_X;
        final int y = topPos + SmartSorterContainerMenu.MODE_Y;
        if (mouseX >= x && mouseX < x + SmartSorterContainerMenu.MODE_WIDTH
            && mouseY >= y && mouseY < y + SmartSorterContainerMenu.MODE_HEIGHT) {
            minecraft.gameMode.handleInventoryButtonClick(
                menu.containerId,
                SmartSorterContainerMenu.ACTION_TOGGLE_MODE
            );
            return true;
        }
    }
    return super.mouseClicked(mouseX, mouseY, button);

```

### S-2 分拣站可能把物品取出来却塞不进去

相关代码：

- `smartsorter/SmartSorterBlockEntity.java:160-171`
- `smartsorter/SmartSorterBlockEntity.java:217-251`

`acceptedAmount()` 只检查：

- 空槽位：按 `stack.getMaxStackSize()`；
- 已有同类物品：按 `existing.getMaxStackSize() - existing.getCount()`。

它没有检查：

- `target.canPlaceItem(slot, stack)`；
- 容器级 `target.getMaxStackSize(stack)`；
- 槽位是否真的允许该物品（熔炉燃料槽、酿造台、模组机器限制槽等）；
- `setItem` 是否会被容器拒绝或截断。

随后代码先 `storage.extract(..., accepted, EXECUTE, ...)`，再 `insertInto()`；如果 `insertInto` 实际只放进去一部分，剩余物品就**从网络消失**。这与 javadoc 的“绝不会出现取出来了却塞不下”相反。

**建议**：

1. 先构建一个“目标槽位计划”：
   - 遍历槽位；
   - 检查 `canPlaceItem`；
   - 用 `getMaxStackSize(stack)` 和槽位实际上限计算可放数量；
   - 得到一个 `plan` 和 `totalAccepted`。
2. 只从网络提取 `totalAccepted`。
3. `insertInto` 严格按计划写入；若实际写入量小于提取量，立即把差额退回网络（`storage.insert(..., EXECUTE, ...)`）或中止本次操作。
4. 若目标容器只暴露物品 Handler/Capability 而不是 `Container`，通过平台适配器处理（见 R-2）。
5. 增加“熔炉/漏斗/只允许特定物品的容器”测试，确认无丢失。

- 分拣站可直接把网络物品抽到面前容器；网络桥可直接把远端网络物品/能量转到本地网络。
- 两者都可以由任意玩家放置、潜行绑定、打开（分拣站），不需要对目标网络有 `OPEN`/`EXTRACT`/`INSERT` 权限。

这是多人服务器上的实际绕过：玩家只要能够接触到别人的网络方块，就能把网络桥指向它，再从自己的网络取走物品。

**建议**：

1. 绑定/打开时立即检查目标网络权限：
   - 分拣站：`OPEN` + `EXTRACT`（以及需要时 `INSERT`）；
   - 网络桥：至少 `EXTRACT` + `INSERT`；
   - 监控仪/接收器：至少 `OPEN` 或 `BUILD`，按产品定位决定。
2. 持久化“授权玩家 UUID”（或网络所有者），在 tick 中定期复核；如果权限变化，停止转发并标记“无权限”。
3. 不能只在客户端检查；服务端 `clickMenuButton`、`useWithoutItem`、`bindTo` 都要检查。
4. 对无主的默认网络（`SecurityNetworkComponent` 默认策略允许）保持可用，避免破坏普通玩家体验。
5. 若决定“物理接触即授权”，必须在 README 明确写出，并关闭安全网络上的桥接/分拣功能，不能静默绕过。

### E-1 Fabric 能量适配器不遵守事务

相关代码：

- `rswirelesscrafting-fabric/.../WirelessEnergyReceiverEnergyStorage.java:16-21`

```java
@Override
public long insert(final long maxAmount, final TransactionContext transaction) {
    return blockEntity.receiveExternalEnergy(maxAmount, false);

```

Team Reborn Energy 的 `insert` 必须在事务提交后才真正生效；如果同一事务中其他参与者失败并回滚，这里已经把能量写进缓冲，回滚不会撤销，造成免费能量/复制。

- 或在 `transaction.addCloseCallback` 中根据 `Commit`/`Abort` 决定是否写入；
- 加一个“事务 abort 后缓冲不增加”的测试。

## 5. P1 详细说明

### M-1 能量监控净收支几乎恒为 0

相关代码：`energymonitor/EnergyMonitorBlockEntity.java:209-219`

当前 `sample()`：

1. `previous = stored`（这个值在 tick 开头刚被 `read()` 设为当前值）；
2. 立刻 `read(resolveNetwork())` 再读一次；
3. 用两次同一时刻的差值算 `netRate`；
4. 结果基本只反映这几行代码之间扣掉的几 FE，净收支显示错误，`getSecondsUntilEmpty()` 也随之错误。

**建议**：保存上一次采样时刻的 `stored` 与 `gameTime`，在下一个采样点用真实时间差计算：

```java
private long lastSampleStored;
private long lastSampleGameTime;

private void sample(final Config.EnergyMonitorEntry config) {
    final long now = level.getGameTime();
    if (lastSampleGameTime != 0L) {
        final long elapsed = Math.max(1L, now - lastSampleGameTime);
        netRate = (stored - lastSampleStored) * 20L / elapsed;
    }
    lastSampleStored = stored;
    lastSampleGameTime = now;
}
```

还要处理：

- 断网/重新绑定时重置基线，避免把“网络消失”算成巨额放电；
- `capacity == 0` 时不要除以容量；
- 用 `long` 溢出保护或 `double` 中间值。

**验收标准**：接入一个稳定 100 FE/s 的负载，监控仪显示约 -100 FE/s；停止负载后回到 0 附近；预计耗尽时间与手算一致。

### S-4 标签模式只搬第一种匹配物品

### N-3 网络桥/分拣站费用未真正生效

相关代码：

- `networkbridge/NetworkBridgeBlockEntity.java:167-176`
- `smartsorter/SmartSorterBlockEntity.java:253-258`

两处都直接调用：

```java
network.getComponent(EnergyNetworkComponent.class).extract(fee);
```

RS 的 `extract` 在余额不足时仍可能返回 0 或部分值，代码没有检查结果，也不阻止后续搬运。于是：

- 网络桥可以在本地网络没电时继续转发物品/能量；
- 分拣站可以在网络没电时继续搬物品。

- 对接收器这种“提供能量”的设备，可以保留宽限，但需要单独定义。

**验收标准**：网络 0 FE 时，桥/分拣站停止搬运或明确进入宽限状态；补电后恢复；费用与搬运量对账一致。

## 6. P2/P3 建议

### P-1 分拣站扫描性能

`findMatch()` 对每个过滤槽都调用一次 `storage.getAll()`；`move()` 最多 9 个槽，`refreshData()` 又 9 次。大网络（几千种物品）会产生明显的每 tick 分配与遍历。

建议：

- 每个 tick 只取一次快照，所有过滤槽复用；
- 为标签模式建立 `TagKey -> 资源` 的缓存，过滤槽变化/网络变化时失效；
- 使用轮转游标，避免每次都从列表头开始。

### L-2 自指接入点不可解析

接收器和监控仪都是普通 `BlockEntity`，不实现 `NetworkNodeContainerProvider`。但它们在无剪贴板时会把自己设为 anchor：

- `WirelessEnergyReceiverBlock.java:118-122`
- `EnergyMonitorBlock.java:135-139`

`BoundTargetResolver` 只识别 `NetworkItemTargetBlockEntity` 或 `NetworkNodeContainerProvider`（`BoundTargetResolver.java:49-62`），因此把接收器/监控仪作为 anchor 后，其他设备绑定它会一直“未连接”。

建议：

- 不要在无有效网络时把自己设为 anchor；
- 或提供明确的“接入点方块”，而不是复用设备自身；
- 或在绑定成功后立即校验 `resolveNetwork(target)`，失败就提示。

### L-3 BoundPosition 空值保存

`BoundPosition.save(tag, null)` 直接返回，不会 remove 旧键。当前 `saveAdditional` 通常拿到新 tag，所以不是必然 bug；但若未来复用 tag 或在同一 tag 上增量写入，会留下旧绑定。建议 null 时显式 `tag.remove(...)`。

### C-2 配置热更新

- `WirelessEnergyReceiverBlockEntity` 的 `capacity` 在构造时 `final` 化（`:59,75`）；
- `NetworkBridgeBlockEntity` 的 `itemLimiter`/`energyLimiter` 在构造时创建（`:53,67`）。

运行中改配置后，tooltip 显示新值，但方块仍按旧值工作。建议每次 tick 读取当前配置，或明确要求重启/重载。

### M-2 数值溢出

`EnergyMonitorBlockEntity` 中：

- `getAnalogOutput()`：`stored * 15`
- `isBelowThreshold()`：`stored * 100`
- `sample()`：`(stored - previous) * 20`

在极端容量下可能溢出。建议用 `double` 或先除后乘，并加 `Math.multiplyExact`/上限保护。`RateLimiter` 的 `usedInWindow += amount` 也可以考虑饱和加法。

### R-1 版本一致性

`rswirelesscrafting-common/build.gradle.kts` 的版本是 `0.1.0`，两个平台模块是 `0.4.1-beta.1`。common 作为嵌入源通常不单独发布，但版本不一致会让构建产物、POM、排查日志混乱。建议统一由根项目或 `gradle.properties` 管理版本。

### R-2 容器兼容性

分拣站只识别 `Container`。很多现代模组只暴露物品 Handler/Capability，不使用原版 `Container`，因此分拣站对它们“看不见”。建议按平台能力适配（NeoForge `IItemHandler`，Fabric `Storage<ItemVariant>`），或至少在 README 明确限制。

### R-3 其他细节

- `BoundTargetResolver.isTargetPresent()` 未被使用，删除或接入绑定校验。
- `SorterMatchMode.CODEC` / `STREAM_CODEC` 未被使用，且 `CODEC` 触发 deprecation 警告；删除或真正用于网络同步。
- `energy_monitor` 的 blockstate 缺 `linked=false,low=true` 变体；正常流程不可达，但命令/调试设置可能产生紫黑模型。可补全变体。
- `wireless_amplifier`/`wireless_bridge` 的战利品表已补，验证通过；不要再回退。
- 新增方块物品默认 `COMMON` 稀有度；如果定位是终局设备，建议统一设置为 `RARE` 或按现有产品风格处理。
- `gen_lang.py` 生成的配置键数量较大，建议同时提交生成后的 lang，而不是只留脚本。

## 10. 值得保留的设计

不要因为整改把这几个正确决策改掉：

1. **接收器不继承 RS 方块实体基类**：避免自动加入本地网络导致同一缓冲被两张网络重复计入。这个判断是正确的。
2. **“给网络充电 = 成为 EnergyProvider”**：RS 的 `EnergyNetworkComponent` 只有 `extract`，这是唯一正道。
3. **距离费复用统一口径**：`LinkDistanceEnergy` 与终端一致，增幅塔折扣也一致。
4. **零自定义数据包 UI**：分拣站用 `clickMenuButton` + `ContainerData`，与现有监控终端一致。
5. **无线桥“断链路不断区块”**：欠费不能释放强加载，否则会造成远端不再 tick 的死锁。这个铁律必须保留。
6. **战利品表补齐**：`wireless_amplifier`/`wireless_bridge` 之前拆了不掉，现在已补；这是必要的修复。
7. **新包 `package-info.java`、双语注释、资源引用完整**：基础工程质量不错，问题集中在收口和边界。
